# Runtime — Phase 3

The runtime keeps the trusted device connected while the dashboard is closed. It provides lifecycle, presence and diagnostics only. Execution is false; voice, audio/screen capture, keyboard/mouse/application control, shell tools and remote desktop are unavailable. No plugin loader or arbitrary command interface exists.

## Process and identity boundaries

The bundled Rust executable has two fixed modes: `--supervise` holds a per-user supervisor lock and starts only its own `--worker`; the worker holds a second lock and owns the runtime event loop. Kernel locks release after crashes, so leftover files do not block recovery. A duplicate launch exits without another active worker. Worker crashes are restarted with bounded jitter; explicit Stop exits successfully and the supervisor stops. On macOS launchd can also recover an unsuccessful supervisor exit. Windows Run starts the supervisor at login; Windows supervisor-process failure itself requires a manual start or next login, while worker failures are supervised automatically.

Tauri is a client. Its process lifetime does not own the helper; dashboard exit/crash cannot drop the worker. Closing Core is also independent: the worker remains available through local IPC and reconnects when Core returns. No process-name scanning, PID kill command, configurable executable, shell command or file-access endpoint is exposed.

The runtime loads the existing device UUID/Ed25519 key without creating an identity. Its independent resume entry prevents dashboard/runtime refresh races. Owner-authenticated native setup transfers a restricted session directly over OS-protected IPC; React sees only safe status. Scope, signed requests, one-use nonces, rotation, expiry, revocation and security revision all reuse Phase 2. Missing credentials stay AUTH_REQUIRED/UNCONFIGURED until owner repair. Revoked trust is never recreated automatically. LOCKDOWN remains visible and blocks runtime session provisioning; ongoing safe inspection does not grant execution.

## Platform lifecycle and startup

macOS 13+: SMAppService registers the bundled Aqua LaunchAgent using `BundleProgram`, in the logged-in GUI session. The helper and plist stay inside the stable application bundle. Registration/status/unregister are explicit native controls. A valid bundled service can initially return Apple's NotFound status before registration; the UI reports NOT_CONFIGURED and permits registration, rather than incorrectly disabling the control. Missing bundle resources remain UNAVAILABLE. OS registration errors expose only error domain/code. NSWorkspace's notification center observes sleep, wake, active/inactive session and logout on the main run loop. The network/IPC loop runs independently on a bounded two-thread Tokio runtime.

Primary design sources: [Apple SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice), [Apple DTS bundled-service guidance](https://developer.apple.com/forums/thread/802443), [Apple helper migration](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos), and [NSWorkspace sleep notification](https://developer.apple.com/documentation/appkit/nsworkspace/willsleepnotification). No legacy root daemon or blind launchctl installation is used.

Windows: the current user's Run key stores a fixed quoted helper path and `--supervise`; no elevation/service installation. A hidden native window observes WM_POWERBROADCAST and WTS session changes, with explicit logout handling. The runtime uses a current-user-only named pipe, remote-client rejection and server SID verification before provisioning. See [Microsoft Run keys](https://learn.microsoft.com/en-us/windows/win32/setupapi/run-and-runonce-registry-keys), [WM_POWERBROADCAST](https://learn.microsoft.com/en-us/windows/win32/power/wm-powerbroadcast), and [Tokio pipe security attributes](https://docs.rs/tokio/latest/tokio/net/windows/named_pipe/struct.ServerOptions.html). Physical Gaming PC acceptance remains intentionally deferred.

Login persistence is never enabled by a build or dashboard launch. Enable/disable and stop are separate controls. macOS unregister stops its managed job; Windows removal prevents subsequent login launches. Keep Core/PostgreSQL running separately; this phase does not install production Core hosting.

## Connection, health and resource bounds

The actor serializes session rotation and heartbeat/report writes. On connect it resumes the scoped session, verifies runtime protocol compatibility, obtains a one-use sync ticket, opens a bounded WebSocket and requests an authoritative sequence-zero snapshot. ONLINE requires that handshake and successful registration. Subsequent snapshots/batches validate device trust, owner security state, sequence ordering and disabled execution. Duplicate updates are idempotent. A reconnect always discards the previous socket/cursor.

Sleep/session-inactive closes transport and reports SUSPENDING when reachable. Wake/session-active increments generation, coalesces immediate reconnects over 500 ms, revalidates credentials and resynchronizes. Missed heartbeat ticks are skipped rather than replayed in a burst. No execution occurs during any lifecycle state.

- HTTP requests: 10-second deadline, 2 MiB bounded response; complete connect attempt: 25-second deadline. WebSocket frame/message: 2 MiB, stale after 45 seconds without frames.
- Reconnect: exponential half-to-full jitter, starting at 0.5–1 second and capped at 30–60 seconds. Repeated transport failure projects OFFLINE. Auth/revocation/update failures stop automatic retry until explicit repair or a lifecycle revalidation; they never issue new trust.
- Presence heartbeat: 30 seconds; Core lease: 90 seconds. One current row per device; the existing bounded 24-hour/approximately-10,000-event stream supports UI sync. Only actual state/capability/instance transitions append runtime audit history.
- IPC: 16 KiB frame limit, eight concurrent handlers, eight queued controls, three-second frame read/write deadlines and bounded response waits. Cancellation/Stop closes sockets and IPC; a stop reply is delivered before shutdown.
- Logging: fixed code/state/time/component/correlation records only. Active log rotates at approximately 1 MiB, retaining three previous files. No URL, HTTP body/header, OS credential or raw exception is logged.

Health distinguishes STARTING, CONNECTING, ONLINE, DEGRADED, OFFLINE, SUSPENDING, STOPPING, AUTH_REQUIRED, REVOKED, UPDATE_REQUIRED, ERROR and UNCONFIGURED. Startup registration and OS observer availability are separately visible. Capability reports are strict; future capabilities cannot be marked available by a client. Safe discovery consists only of platform/architecture, own version/build and lifecycle facts, without unrelated files/apps/history or hardware fingerprinting.

Final [hosted validation](https://github.com/Taxcut/JARVIS/actions/runs/36268611479) on `7d739d5e70b35dcf7092560f6f56704033999c03` passed Linux TypeScript/PostgreSQL and macOS/Windows native checks, tests and builds. The closure commit changes documentation only. See IMPLEMENTATION_STATUS for the complete acceptance record. Initial hosted validation on `88796f4` passed Linux TypeScript/database and macOS/Windows native jobs: [Validate](https://github.com/Taxcut/JARVIS/actions/runs/35643731767).

Physical Mac evidence on 2026-09-21 through 2026-09-26: the owner approved the helper's real Keychain access; the helper loaded the existing trusted device, used a separately persisted runtime session and reached ONLINE. The original worker survived multiple naturally occurring OS sleep/session notifications, including a long suspended interval. After Core was restored on September 26, the same process automatically refreshed, resynchronized and returned ONLINE. Quit/reopen of the real dashboard preserved the same runtime instance. A duplicate supervisor invocation created no competing worker.

SMAppService registration launched a new launchd-owned supervisor/worker from `~/Applications/JARVIS.app`; the worker resumed the existing device/session. A controlled SIGKILL of only that worker produced WORKER_RESTARTING, a new worker/instance and ONLINE within approximately one second, retaining the device identity. Disable startup removed the job and the dashboard reported DISABLED and OFFLINE. No forced logout or reboot was required; full login-after-reboot remains a longer production acceptance check.

Final installed-build check on September 26: a fresh complete bundle replacement followed by explicit registration reached ONLINE with startup ENABLED, the original trusted Mac, one active restricted runtime session and one current presence row. The database still had one owner, one trusted device, one passkey and eight unused recovery-code hashes. Dashboard quit/reopen preserved the same final instance. Diagnostics showed current heartbeats, the OS observer, no error and all future capabilities UNAVAILABLE. The runtime is left running with login startup enabled. An earlier in-place bundle replacement was rejected by macOS launch constraints despite valid on-disk signatures; replacing the stopped bundle as a unit resolved it without weakening OS security. See JARVISSETUP.

A 30-second spot sample of the original idle debug runtime (seven samples at five-second intervals) reported 0.0% CPU in `ps` for supervisor/worker; supervisor RSS was 816–832 KiB and worker RSS 5,088–9,264 KiB after several days including sleep. These are observed samples on this Mac, not peak-memory guarantees or release benchmarks. The desktop/Core/PostgreSQL are excluded; host memory compression and concurrent build activity can affect RSS.

Ad-hoc signing is used for local validation, with `codesign --verify --deep --strict` passing. Developer ID signing/notarization, hardened distribution/update policy, VPS/private networking, production backups, voice and execution remain future phases. See SECURITY for same-user compromise assumptions and JARVISSETUP for the deferred physical Windows checklist.

## Failure-mode review

The following separates automated/physical evidence from reviewed behavior; no destructive recovery or Windows physical test is implied.

| Scenario                                                          | Evidence and behavior                                                                                                                                                                                                                          |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Core unavailable at launch or lost while connected, then restored | Connection paths reviewed; physical outage/recovery kept the worker and device alive and returned ONLINE. Transport/5xx errors use bounded jitter; after repeated failures local state becomes OFFLINE.                                        |
| Network interruption or database unavailable behind Core          | Reviewed transport timeout, closed/stale WebSocket and Core error paths. No general network isolation or owner-database shutdown was forced. Responses fail closed and retry with the same bounded policy.                                     |
| Sleep, long sleep, wake and session transitions                   | Real OS notifications over September 21–26 plus deterministic lifecycle tests. Sockets are discarded; resume refreshes and requests an authoritative snapshot.                                                                                 |
| Access/session expiry, revocation and LOCKDOWN                    | Real-cryptography integration tests cover refresh rotation, revocation/socket closure, security revisions and lockdown provisioning denial; native tests/review cover terminal auth/revocation classification. No trusted device is recreated. |
| Runtime crash, restart, duplicate launch and stale lock files     | Physical worker crash/restart and duplicate invocation; kernel-lock release tests and IPC tests. Exactly one supervisor/worker pair and one presence row remain.                                                                               |
| Autostart disabled or installed build replaced                    | Physical supported registration/unregister/re-register; fresh bundle replacement verified. Full reboot/login is deferred.                                                                                                                      |
| Incompatible protocol or malformed Core response                  | Integration protocol rejection; native compatibility/size bounds, malformed-message and sequence-validation review/tests. No execution is granted.                                                                                             |
| Replay gap or duplicate events                                    | PostgreSQL replay-gap test supplies authoritative snapshot; runtime reconnect always starts at sequence zero. Native sequence checks reject rollback and ignore already-applied updates.                                                       |
| Shutdown during reconnect                                         | Reviewed serialized actor, bounded connect/HTTP timeouts, signal/control shutdown and stop acknowledgement; IPC clean-shutdown test. A stop may wait for the bounded in-flight operation.                                                      |
| Dashboard quit/restart                                            | Physically checked with both earlier and final installed builds; runtime instance and trusted device are unchanged.                                                                                                                            |

Same-user/admin compromise, production code signing/update delivery and Windows supervisor-process failure limits remain explicit in SECURITY and the lifecycle section above.
